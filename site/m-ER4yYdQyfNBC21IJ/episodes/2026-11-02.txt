Okay, something you've been learning. Remember wiring up the memo so a push makes the audio and updates the feed? You know a fresh computer spins up, does the work, and gets thrown away. Here's the part that's a little strange about it. The repo is public, but that computer still needs a private key to talk to the voice service. So how does it get one without everyone seeing it?

The answer is something GitHub calls secrets. You paste the key into the repo's settings once. GitHub stores it encrypted, and after that, nobody can read it back out, not even you. You can only replace it.

When a run starts, GitHub hands the key to that throwaway computer, just for that job. The steps use it, and when the computer's thrown away, the key goes with it.

There's a second layer, too. The logs from each run are public, so GitHub watches the output. If the key ever shows up in a log line, it gets swapped for a row of stars before anyone sees it.

And here's the guardrail that matters most for a public repo. If a stranger copies your repo and sends you a change, the run that tests their change doesn't get your secrets. Otherwise anyone could write a step that just mails your key to themselves.

The weak spot is the steps you write yourself. If a step sends the key somewhere it shouldn't, GitHub can't stop that. The safe stuff is automatic. Being careful with your own steps is still on you.
